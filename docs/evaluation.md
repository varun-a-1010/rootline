# Evaluation

How Rootline's multi-agent orchestrations were compared with a single-agent baseline, and what
the numbers show. Every number on this page comes from `eval/results/` (generated by
`eval/summarize.ts` and `eval/judge.ts` from the recorded runs in `eval/runs/`); none is
typed by hand.

## What was compared

| Arm | Design |
| --- | --- |
| **A** | Split by source, then critique. **The multi-agent implementation** in the headline comparison (declared before any held-out run, `eval/results/plan.json`). |
| B | Causes first: candidate causes before any tool call, then tasks that discriminate them. |
| C | A without the critic (one round). Shows what the critic is worth. |
| D | Jev-assisted: the dev-picked base arm plus Jev screening, grading and citation checks. |
| **E** | **Single-agent baseline**: one agent, all five tools, one sequential tool loop. |

Every arm uses the same model (`gemini-3.8-flash`, thinking level `medium`), objective text,
tools, tool runner, evidence ledger, fault injection, budgets (40 tool calls, 48 model calls,
2,000,000 tokens, 6-minute deadline) and report schema, and the same report post-processing.
The baseline is not one-shot: it iterates until it submits or runs out of budget. It runs
sequentially, while the multi-agent arms run tasks in parallel.

## Incidents

14 scenarios × 2 variants = 28 worlds (`docs/scenarios.md`): misleading evidence (s01-s04,
s06-s11), conflicting observations (s05, s14), tool failures (s13, s14 by design; s12 through
missing data; random transient faults everywhere), and two scenarios whose correct outcome is
**inconclusive** (s12, s14).

- **Dev split:** s01, s02, s04, s06, s12, s13, variant A. Used to check the system end to end,
  measure cost per run and pick arm D's base. No prompt changed after the dev runs.
- **Held out:** the other eight A variants and every B variant.

## Protocol

1. The plan (coverage order, budget, headline comparison, arm D base rule) was recorded before
   any held-out run: `eval/results/plan.json`.
2. **Dev phase:** 18 runs (the six dev scenarios on arms A, B and E), $9.86 estimated. They
   measured cost per run (about $0.3-0.9) and picked arm D's base by the pre-registered rule
   (B earned 6/6, A 5/6, so **D's base is B**). They also exposed three engine problems: Vertex
   429 quota errors with too-short backoff, the baseline falling back to the multi-agent
   reporting agent at the deadline, and budget stops masking a critic's decision. These were
   fixed before the freeze.
3. **Freeze:** prompts frozen with hash `fbb5303b5fc5eeaa` (`eval/results/freeze.json`).
   Because the engine changed after the dev runs, they are archived in `eval/runs-dev/` and not
   scored; every scored run, dev scenarios included, was made after the freeze. This is
   stricter than the plan, which would have kept them, and is recorded in `freeze.json`.
4. **Budget:** $50 in total, so the scored runs had $40.14 after the dev phase.
5. **Interruptions and redone runs, all of them.**
   - Eight minutes in, a coding-session restart killed the runner, losing two in-flight runs
     before they wrote a file. They restarted from scratch and their partial spend is unknown.
   - After 25 runs the log showed baseline runs ending `failed` at the deadline. The cause was
     an engine bug in the baseline's final report turn, not the agent's work
     (`eval/runs-superseded/README.md`). The runner was stopped on purpose, losing two more
     in-flight runs, the bug was fixed, and the affected baseline runs were redone. Their
     originals are kept in `eval/runs-superseded/` and still count toward the budget.
   - The cap was lowered to $39.14 ($0.50 per interruption, an estimate for the unrecorded
     spend) so the total stays within $50. The engine changed at this point, so scored runs
     span two git SHAs, recorded per run; only the baseline's deadline path differs.
   - The cap was later raised to $89.14 at list rates, because the owner confirmed Google's
     half pricing applies on Vertex AI: the $50 budget is real money, so it buys $100 at the
     list rates these estimates use, less the dev phase and the unrecorded allowance. That
     let every arm run on every world. Repetitions were not run.
   - During step 4 and 5 live checks two processes opened the same PGlite directory, which
     PGlite does not support. `eval/verify-worlds.ts` found all 28 worlds in that directory
     identical to the fixtures, so no run read damaged data.
6. Runs execute through `npm run eval`. Arms A and E, and the first 26 runs of arms B, C and D,
   ran at concurrency 2. To finish sooner, the last 58 runs (all arms B, C and D) ran at
   concurrency 4. That was a mistake for reliability: see **Run failures** below. Each run file in `eval/runs/` holds the
   full event log, the report, the metrics and the environment (model, versions reported by the
   API, thinking level, budgets, prompt hash, fixture hash, git SHA, machine). Crashed runs are
   recorded as failed and never silently rerun.
7. Scoring follows `eval/rubric.md` (deterministic) and `eval/judge-questions.md` (Jev judge,
   blind to the arm, validated first on `eval/judge-validation/`).

## Metrics

- **Root-cause accuracy:** top hypothesis's (component, cause type) against the label, credited
  only when the report commits to a conclusive outcome; partial credit as labeled; s05 needs both
  causes in the top two. Top-2 hit rate is supplementary.
- **Inconclusive handling:** correct abstentions and unsupported definitive diagnoses on s12/s14;
  false abstentions on the conclusive scenarios.
- **Evidence grounding:** fabricated-citation rate (cited ids that do not exist in the run's
  ledger), facts stated without evidence, required-evidence recall; judged claim support and
  counterevidence addressed when the judge is available.
- **Tool calls:** calls, attempts, retries, failures, partial results.
- **Latency:** wall clock from the first to the last event of the run.
- **Tokens:** input, output, thinking and cached input per run, from provider-reported usage
  (unknown is shown as unknown). A dollar estimate at standard rates sits beside them.

## Results

Five arms on 28 worlds: 140 scored runs, one each. No repetitions were run, so no result here
measures run-to-run variance. Model versions, budgets, prompt hash, fixture hash and the commit
are in each run file. The runs span commits `129a467` to `b2f6623`. Across that span the only
change to agent code is the baseline's deadline-turn fix (`eval/runs-superseded/README.md`); the
others touched pricing metadata, a test helper and a web route. Later commits (see **After the
evaluation**) are not covered by these numbers.

**Spend:** $74.62 estimated at list rates across all recorded runs (scored $64.17, dev $9.86,
superseded $0.58), which is about $37 at the half pricing in force, plus the two estimated
allowances for unrecorded runs. Inside the $50 budget.

### What the numbers show

- **Multi-agent did not clearly beat the single agent.** Arm A earned 21.5 of 24 on root cause
  and the baseline 20 of 24 (held out: 16.5 and 15 of 19). A gap of 1.5 cases on 24 is within
  noise, and no arm separates from the others: the range is 20 to 21.5.
- **Every arm is poor at saying "we don't know", and this is the main finding.** On the two
  scenarios that should end inconclusive, 15 of 20 runs gave a definite diagnosis. Arms A, B, C
  and D earned 0 of 4 correct abstentions; the baseline earned 2 of 4. One of those two was the
  model's own decision. The other was the code's honesty rule downgrading a conclusive report
  after the budget ran out.
- **The critic did not stop a single unsupported diagnosis.** All 10 in the critic arms (A, B, D)
  were accepted by the critic, typically by elimination: internal services look healthy, so it
  must be the partner. In 84 runs the critic declared the evidence insufficient once, and that
  was on a scenario with a definite answer (s07-B, a false abstention).
- **What the critic did buy is evidence, at a price.** Against arm C (no critic), arm A found
  more of the required evidence (94.6% vs 82.1%) but cost 57% more ($0.51 vs $0.32) and took 47%
  longer (225 s vs 153 s), with no measurable accuracy gain (21.5 vs 21).
- **The baseline is cheaper, and no slower.** It sends over three times the input (874,019 vs
  254,343 tokens per run) but 84% of it is cached, against 24% for arm A, so it costs $0.42 to arm
  A's $0.51. Latency is about equal (220 s vs 225 s) despite arm A's parallelism.
- **Causes first (B) made no difference.** It matched arm A on accuracy, though it won the dev
  pick that made it arm D's base.
- **Jev did not save money.** Arm D cost $0.53 per run against its base arm's $0.51, with about
  the same input tokens. The brief asked Jev to take work away from Flash; in these runs it did
  not.
- **Citations are real.** 3 of 17,099 cited ids did not exist. That says the ids are real, not
  that the evidence supports the claim; claim support needs the judge.
- **One label looks too strict, and was left alone.** On s01-B, four of five arms named the right
  component and the real mechanism (the import was OOM-killed) as `capacity_saturation`. The
  frozen label accepts only `data_pipeline_failure`, so they scored 0. The fifth got partial
  credit. Fixing the label after seeing results would be tuning the answer key.

### Where the arms differ

From `eval/results/differences.md`, generated from the run files and labels by
`eval/differences.ts`. 17 of the 28 incidents scored the same in all five arms. On the other 11:

- **Multi-agent ahead of the baseline.** `s06-B`, the held-out SIP double debit, is the clearest
  case. All four multi-agent arms named the deployment that shortened the debit timeout. The
  baseline's report saw the timeout mismatch but put the root cause on the bank's latency
  (`debit-worker / upstream_dependency_degradation`). On `s13-B`, the held-out payout delay where
  the metrics tool keeps timing out, arms A and B scored and the baseline did not. That is a
  scoring difference more than a reasoning one: the baseline's report describes the lock (an
  export job's `FOR UPDATE` query) but files it under `job-scheduler / data_pipeline_failure`.
  The deterministic score checks component and cause type, and the mechanism judge did not run.
  On `s05-A` (two causes), arms B and D covered both and the baseline one. Arm C alone was ahead
  on `s01-B` and `s05-B`.
- **Baseline ahead:** the two correct abstentions (`s12-A`, `s14-A`), and single arms on `s10-A`
  (A, half credit), `s07-B` (B, a false abstention), `s02-A` (D, an inconclusive report) and
  `s06-A` (C, an inconclusive report).
- **What the critic loop changed.** Comparing each run's first reasoning version with its final
  report, the top cause changed in 5 runs: `s01-A` and `s02-B` in arm A, `s05-A` in B, `s06-B`
  and `s10-A` in D. All five went from wrong to right, and no run went the other way. In
  `s06-B-D` the first version blamed the bank (`bank-connector / upstream_dependency_degradation`),
  as the baseline's report did, and the follow-up round moved it to the deployment that shortened
  the timeout. The caveat matters: arm C, which has no critic, got
  four of those five incidents right in a single round. The loop mostly recovered from a bad
  first draft rather than reaching answers one round could not, which is why it does not show
  as an accuracy gain over arm C.

### Run failures

Six of 140 runs ended `failed`, all from Vertex problems and none from an agent's reasoning.
Failed runs score as failed and were not rerun. The figures here come from
`eval/results/run-health.md`, generated from the run files by `eval/run-health.ts`.

| Run | What happened |
| --- | --- |
| `s06-A-C`, `s12-A-C` | The plan call hit two 429s and then a 90 s hang, so the run did no investigation at all |
| `s02-A-D`, `s13-B-D`, `s14-A-A`, `s14-B-B` | The report call hung; the retry ran out of the fixed 120 s allowance, so a code-built report was used |

| Period | Runs | Failed | 429 errors | Hung requests |
| --- | --- | --- | --- | --- |
| Concurrency 2 | 82 | 1 (1.2%) | 2 | 12 |
| Concurrency 4 | 58 | 5 (8.6%) | 14 | 28 |

Raising concurrency to finish sooner cost reliability, and five of the six failures fell on arms
B, C and D. Arms A and E ran entirely at concurrency 2, so the headline comparison is unaffected,
but arms B, C and D are somewhat understated. The row "Top hypothesis matches (any outcome)" shows
what those runs had found where a report exists: A 22, B 23, C 22, D 23, E 21 of 24.

### Judged metrics

The model judge (mechanism agreement, claim support, counterevidence addressed) was validated at
37 of 40 on the agent-labeled set: mechanism 20 of 20, claims 17 of 20. All three disagreements
were the judge rejecting a supported claim, two of them needing a UTC-to-IST conversion, so claim
support is likely conservative. **The judged metrics were not produced.** OpenRouter refused
further calls with a 402 billing error after 26 of 140 runs (s01, s02 and part of s03), and those
26 are not a fair sample, so they are not reported. The partial results are in
`eval/results/judge.json`, and the judge resumes from there. Until it finishes, claim support and
mechanism agreement are unmeasured, and only the deterministic metrics above stand.

### What this evaluation cannot show

14 scenarios, two variants, one run each, labeled by the agent that wrote them. Treat every
difference above as a lead, not a measurement. See `docs/limitations.md`.

## After the evaluation

Everything here came after scoring and changes none of the numbers above. The comparison is one run
per configuration on four dev scenarios, so it can show a failure or a large effect, not a small
improvement. All 16 runs are in `eval/runs-post/` and listed in
`eval/results/post-evaluation.md`; they cost $4.24 at list rates.

**The goal was cheaper live runs before sharing the demo, and that did not happen.** On the three
conclusive scenarios, which no hung plan call cut short, cost per run did not move beyond noise:

| Arm A configuration | Root cause | Est. cost per run | Input tokens | Cached | Specialist cached | Synthesis cached tokens |
| --- | --- | --- | --- | --- | --- | --- |
| Evaluated | 3 of 3 | $0.481 | 242,327 | 23.9% | 31.9% | 0 |
| Reordered prompts (reverted) | 3 of 3 | $0.475 | 218,895 | 19.5% | 29% | 0 |
| Final code | 3 of 3 | $0.493 | 255,363 | 33.9% | 45.8% | 0 |

- **Smaller tool output (kept).** `query_logs` now returns 25 rows by default and `query_metrics` 60
  points. There is no measurable saving: input was 255,363 tokens per run against
  242,327, because how much a run investigates matters more. `scenarios/review.ts`
  confirms all required evidence is still reachable at these limits.
- **Reordered prompts (reverted).** Putting shared context first was meant to let the synthesis
  agents hit the cache. They got no cached tokens either way, so the change was undone.
- **Forced final turn (kept).** It stays an ordinary request the first time. Specialist cached share
  rose to 45.8% from 31.9%, the only visible caching gain, but
  it did not show up as lower cost in these runs.
- **Recovery (kept).** A failed plan call now falls back to the default plan, and the report call
  gets a longer grace period. A real failure tested the first: on s12-A the plan call hung three
  times. In the evaluation that failure ended `s06-A-C` and `s12-A-C` with no investigation. This
  run made 11 tool calls instead, then reached the deadline inconclusive with
  0 of 2 required evidence. That is lost time, not a correct abstention.

### What implicit caching needs

Each condition sends a fresh prompt twice, 6 s apart, four times over
(`eval/results/cache-experiment.md`):

| Condition | Repeats with a hit | Mean cached on repeat | Cached tokens per pair | Cold first calls |
| --- | --- | --- | --- | --- |
| plain text, repeated | 4 of 4 | 83% | 16352, 16352, 16352, 16352 | 4 of 4 |
| same responseSchema, repeated | 4 of 4 | 82% | 16266, 16266, 16266, 16266 | 4 of 4 |
| different responseSchema on the repeat | 0 of 4 | 0% | 0, 0, 0, 0 | 4 of 4 |
| same tools, repeated | 3 of 4 | 62% | 16313, 16313, 0, 16313 | 4 of 4 |
| tools, then restricted to one function | 0 of 4 | 0% | 0, 0, 0, 0 | 4 of 4 |

A repeat hits when the whole request matches, not just its text. Reasoning, critic and reporting
each have their own output schema, so a shared text prefix cannot hit. That is why reordering did
nothing, and why those agents, 38.7% of arm A's cost, ran effectively uncached. Restricted
functions also missed, which is why the forced turn changed. Caching stays best-effort: identical
tools missed once in four.

An earlier single-pair test showed no hit for a repeated schema, and commit `c192ef1` blames
structured output on that basis. **That explanation was wrong.** A rerun contradicted it and these
repeats settle it. Reverting the reordering still stands, because that was measured on real runs.

Untested: giving the synthesis agents one shared tool list, with their outputs as functions, could
make those calls cacheable.

### Flash-Lite

Gemini 3.5 Flash-Lite cost about a tenth as much ($0.065 on arm A and
$0.025 on arm E, against $0.481 and $0.489) but found the root cause
in 1 of 3 and 2 of 3, against 3 of 3 for both 3.8 Flash arms. On s04, both Flash-Lite arms blamed
`order-service` capacity, the scenario's planted trap. It is not a safe demo model on this
evidence, so 3.8 Flash stays the default.

### What actually limits the demo's cost

Not per-run savings: the access code and the limit of 10 live runs a day do. If a lower per-run
cost is needed, arm C is the evaluated option: $0.347 per completed run against arm A's
$0.513, with similar root-cause accuracy (21 and 21.5 of 24) but less required evidence
found (82.1% and 94.6%) and no critic. The default has not been changed.
