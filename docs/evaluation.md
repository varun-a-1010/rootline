# Evaluation

How Rootline's multi-agent orchestrations were compared with a single-agent baseline, and what
the numbers show. Every number on this page comes from `eval/results/` (generated by
`eval/summarize.ts` and `eval/judge.ts` from the recorded runs in `eval/runs/`); none is
typed by hand.

## What was compared

| Arm | Design |
| --- | --- |
| **A** | Split by source, then critique. **The multi-agent implementation** in the headline comparison (declared before any held-out run, `eval/results/plan.json`). |
| B | Causes first: candidate causes before any tool call, then tasks that discriminate them. |
| C | A without the critic (one round). Shows what the critic is worth. |
| D | Jev-assisted: the dev-picked base arm plus Jev screening, grading and citation checks. |
| **E** | **Single-agent baseline**: one agent, all five tools, one sequential tool loop. |

Every arm uses the same model (`gemini-3.8-flash`, thinking level `medium`), objective text,
tools, tool runner, evidence ledger, fault injection, budgets (40 tool calls, 48 model calls,
2,000,000 tokens, 6-minute deadline) and report schema, and the same report post-processing.
The baseline is not one-shot: it iterates until it submits or runs out of budget. It runs
sequentially, while the multi-agent arms run tasks in parallel.

## Incidents

14 scenarios × 2 variants = 28 worlds (`docs/scenarios.md`): misleading evidence (s01-s04,
s06-s11), conflicting observations (s05, s14), tool failures (s13, s14 by design; s12 through
missing data; random transient faults everywhere), and two scenarios whose correct outcome is
**inconclusive** (s12, s14).

- **Dev split:** s01, s02, s04, s06, s12, s13, variant A. Used to check the system end to end,
  measure cost per run and pick arm D's base. No prompt changed after the dev runs.
- **Held out:** the other eight A variants and every B variant.

## Protocol

1. The plan (coverage order, budget, headline comparison, arm D base rule) was recorded before
   any held-out run: `eval/results/plan.json`.
2. Prompts were frozen and their hash recorded: `eval/results/freeze.json`. Only runs with the
   frozen prompt hash are scored.
3. Runs execute at concurrency 2 through `npm run eval`. Each run file in `eval/runs/` holds the
   full event log, the report, the metrics and the environment (model, versions reported by the
   API, thinking level, budgets, prompt hash, fixture hash, git SHA, machine). Crashed runs are
   recorded as failed and never silently rerun.
4. Scoring follows `eval/rubric.md` (deterministic) and `eval/judge-questions.md` (Jev judge,
   blind to the arm, validated first on `eval/judge-validation/`).

## Metrics

- **Root-cause accuracy:** top hypothesis's (component, cause type) against the label, credited
  only when the report commits to a conclusive outcome; partial credit as labeled; s05 needs both
  causes in the top two. Top-2 hit rate is supplementary.
- **Inconclusive handling:** correct abstentions and unsupported definitive diagnoses on s12/s14;
  false abstentions on the conclusive scenarios.
- **Evidence grounding:** fabricated-citation rate (cited ids that do not exist in the run's
  ledger), facts stated without evidence, required-evidence recall; judged claim support and
  counterevidence addressed when the judge is available.
- **Tool calls:** calls, attempts, retries, failures, partial results.
- **Latency:** wall clock from the first to the last event of the run.
- **Tokens:** input, output, thinking and cached input per run, from provider-reported usage
  (unknown is shown as unknown). A dollar estimate at standard rates sits beside them.
