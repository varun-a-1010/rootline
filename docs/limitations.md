# Limitations, incomplete functionality and external dependencies

Honest notes on what Rootline does not do, what its evaluation cannot show, and what it depends
on. The evaluation-specific items at the end are filled in from `eval/results/`.

## The data is synthetic

- Every service, incident, metric, log line, bank, fund and person is generated by
  `scenarios/` from seeded random numbers. Realism comes from market-hours traffic, background
  noise, routine deploys and past incidents, but it is still a model of a system, not a system.
- Each scenario has a designed trap and a designed answer. Real incidents are messier: several
  partial causes, missing ownership, telemetry nobody kept.
- Metric points carry at most one label, and data older than the high-resolution range exists
  only as 5-minute rollups. Log volume is a few thousand lines per world.

## The labels were reviewed by the agent that wrote them

- The answer keys (`eval/labels/`) and the evidence-sufficiency review (`docs/scenarios.md`)
  were produced by the coding agent, not by a human. An author reviewing its own scenarios can
  share their blind spots.
- The same agent wrote the scenarios and the prompts. Prompts were kept generic (no scenario
  facts) and iterated only on dev scenarios, but the author knew the held-out scenarios when
  writing them. That is a form of leakage the held-out split cannot fully remove.
- Scenario s11's investigation window is a trading day (about 7 hours) rather than 3-4 hours,
  so that the misread deploy timestamp stays inside it.

## Small samples and model variance

- 14 scenarios, each with two variants (28 worlds). Differences of one or two cases between arms
  are within noise; the evaluation reports counts and avoids claims the counts do not support.
- Gemini 3.8 Flash does not accept a seed or temperature, so runs are not reproducible; repeated
  runs measure variance rather than remove it.
- Confidence values are model estimates, not calibrated probabilities.

## The judge

- Jev judges every arm and also makes decisions inside arm D. The judge is blind to the arm, but
  the overlap is a risk for arm D's judged numbers.
- The judge was validated on 40 items labeled by the coding agent, not by a human. Its agreement
  on that set is reported in `eval/results/`; it is a check, not a guarantee.
- No human reviewed claim support or grounding.

## Design choices that limit the comparison

- The single-agent baseline runs sequentially; the multi-agent arms run tasks in parallel. Both
  get the same budgets (tool calls, model calls, tokens, deadline), tools, faults and report
  schema, but wall-clock latency reflects the concurrency difference as well as the design.
- Budgets differ from the brief's starting defaults: 48 model calls (not 30) and 6 tool calls per
  specialist task (not 8). The first live run showed 30 model calls starve the critic's
  follow-up rounds. The final report call is always allowed once, for every arm.
- The run deadline is 6 minutes. Runs that reach it stop investigating and report what they have,
  with the stop reason `deadline`.
- Cost figures are estimates at standard list rates (`src/llm/pricing.ts`): Gemini 3.8 Flash
  $1.50/M input, $7.50/M output including thinking, $0.15/M cached input; Jev $0.042/M input.
  Promotional credits are ignored. Tokens are the primary measure.
- The model's "thinking" tokens dominate output for the synthesis agents; they are reported but
  their content is not inspected.

## Functionality that is incomplete or simplified

- Tools are read-only queries over a synthetic store. Rootline recommends actions and never
  executes them.
- The critic's follow-ups are limited to concrete tool calls (at most 4 per round, 3 rounds).
- Arm D's screening only applies to log, change and incident results with at least 8 records;
  metric series are not screened.
- The web UI is deliberately plain and was not visually verified by the coding agent (the owner
  does visual QA). It is covered by API tests, a type check and a production build.
- Live runs from the web UI are rate-limited and need an access code on the hosted demo.

## External dependencies

| Dependency | Used for | Without it |
| --- | --- | --- |
| Vertex AI, Gemini 3.8 Flash | every agent and the baseline | `npm test`, the UI's recorded runs and the evaluation results still work; live runs do not |
| OpenRouter, Jev (`typesafe/jev-1.13`) | arm D, evaluation judge | arms A, B, C, E and deterministic scoring work; arm D and judged metrics do not |
| Agentflow viewer (`flow.slate-app.online`) | animated graph in the run view | the rest of the run view works |
| Deltabase-hosted Postgres | hosted demo database | PGlite is used locally and in tests |
| npm packages | see `package.json` | — |

The Jev 1.13 model page on OpenRouter was not reachable during the build (its hub lists 1.14 as
current and 1.13 as still available); its price is taken from TypeSafe's documentation.
